# Security

## Summary

The platform applies defence in depth: network isolation between tiers, no
inbound SSH, encrypted data at rest, secrets in SSM SecureString, least-privilege
IAM, and automated checks (`tfsec` + OPA policy) that gate every change before it
can reach `main`. Compliance posture is measured continuously with AWS Config and
periodically with Prowler against CIS AWS Benchmark 2.0.

## Security controls implemented

| Domain | Control |
|---|---|
| **Network** | Public/private subnet split; app and DB tiers have no route to the internet except outbound via the NAT instance; security groups chained by reference (ALB → app → DB), no CIDR-based app/DB ingress |
| **Access** | No SSH key pairs, no port 22 ingress; shell access only via SSM Session Manager; IMDSv2 required on all instances (token-based, blocks SSRF-style metadata theft) |
| **Data at rest** | RDS storage encrypted (KMS); all EBS volumes encrypted (root + gp3); S3 buckets (state, artifacts, config) encrypted with SSE; `alerts-email` SNS topic encrypted (`alias/aws/sns`); `alerts` SNS topic unencrypted (see *Known risks* — CloudWatch Alarms cannot use the AWS-managed key) |
| **Data in transit** | ALB ↔ instance and instance ↔ RDS traffic stays inside the VPC. Public HTTP:80 only — no TLS (no ACM certificate; documented trade-off) |
| **Secrets** | DB master password and Flask session key generated by Terraform, stored as SSM **SecureString**, read by instances at boot via a scoped IAM policy; never in state outputs, never committed |
| **Supply chain** | `tfsec` HIGH gate + OPA/Conftest policy on every PR; branch protection blocks direct pushes; drift detection catches out-of-band changes |
| **Audit** | VPC Flow Logs (all traffic → CloudWatch); AWS Config records 7 resource types; CloudWatch alarms → SNS email |

### CI user least-privilege

The CI user (`ce-capstone-ci`) started with `AdministratorAccess` as an
unblocking measure and was later scoped to `docs/ci-policy.json`:

- Full access to the services Terraform manages: `ec2`, `elasticloadbalancing`,
  `autoscaling`, `rds`, `cloudwatch`, `logs`, `sns`, `ssm`, `config`; `lambda`
  scoped to `function:ce-capstone-*`.
- KMS limited to read / grant / decrypt actions (only AWS-managed keys are used).
- **IAM scoped to `role/ce-capstone-*` and `instance-profile/ce-capstone-*`
  only**; `iam:PassRole` further conditioned to the four services that need it
  (EC2, VPC Flow Logs, Config, Lambda).
- **S3 scoped to the three project bucket prefixes only**
  (`ce-capstone-tfstate-*`, `ce-capstone-artifacts-*`, `ce-capstone-config-*`).
- **DynamoDB scoped to the single lock table.**

This is *scoped by service, not by individual resource ARN* — a pragmatic
middle ground for the project timeline. A production policy would pin every
resource ARN and drop the service wildcards.

## Network security strategy

- Nothing in the application or data tier is reachable from the internet.
- The only internet-facing component is the ALB, on HTTP:80.
- The NAT instance provides **outbound-only** internet for the private tier
  (OS packages, SSM, CloudWatch). Its security group allows ingress only from
  the VPC CIDR.
- VPC Flow Logs capture all accepted and rejected traffic for later analysis.

## Account-level baseline

Two account-wide defaults are set as code (in `modules/compute`) as
defence-in-depth, so any resource created *without* explicit settings still
inherits a safe default:

- `aws_ec2_instance_metadata_defaults` — IMDSv2 required by default for all EC2
  instances in the region.
- `aws_s3_account_public_access_block` — S3 Block Public Access enforced at the
  account level.

Both are redundant with the per-resource settings this stack already applies
(every launch template requires IMDSv2; every bucket has its own public-access
block); they exist to close two CIS/Prowler findings and to protect against
future mistakes. In a production organisation these account-level defaults would
live in a dedicated account-baseline stack, not in a workload stack — they are
managed here for the scope and lifetime of the capstone.

|---|---|---|

Both generated secrets were **rotated** during the Wednesday security pass

-replace=module.data.random_password.app_secret`) as a precaution after a

## Security testing results

### `tfsec` (IaC static analysis, HIGH gate on every PR)

Result: **0 HIGH, 0 CRITICAL.** Findings were either fixed or excluded with a
documented reason in `terraform/.tfsec/config.yml`:

| Fixed | Excluded (with rationale) |
|---|---|
| `alerts-email` SNS encryption; NAT instance IMDSv2 + encrypted root; artifacts & config bucket SSE; ALB `drop_invalid_header_fields` | Public ALB / SG :80 (it *is* the web tier); public egress (NAT + app need it); public IP on public subnets (ALB + NAT live there); customer-managed KMS keys for S3 / CloudWatch / SSM / SNS (Free-Tier: AWS-managed keys); IAM wildcards already scoped to one ARN; **`alerts` topic left unencrypted** (CloudWatch Alarms cannot publish to a topic encrypted with `alias/aws/sns`, and a CMK is out of Free-Tier scope) |

The gate caught a real issue mid-project: an unencrypted SNS topic was blocked
until it was reviewed. The `alerts-email` topic (Lambda-published) now uses
`alias/aws/sns`; the `alerts` topic (CloudWatch-published) is a documented
exception — see *Known risks*.

### OPA / Conftest policy (`policy/terraform.rego`, on every PR)

Enforces: every resource carries a `Project` tag; no security group other than
the ALB allows `0.0.0.0/0` ingress; RDS storage must be encrypted; every S3
bucket must have a public-access block. See
[ADR 0003](docs/decisions/0003-policy-as-code.md).

### AWS Config (continuous)

Five managed rules evaluating: `restricted-ssh`,
`s3-bucket-public-read-prohibited`, `encrypted-volumes`,
`rds-storage-encrypted`, `vpc-flow-logs-enabled`. Compliance results captured
in the presentation screenshots; the recorder is stopped after evidence
capture to avoid ongoing cost.

### Prowler (CIS AWS Benchmark 2.0, scoped to project services)

`docs/prowler-ce-capstone.html` / `.csv`. Findings triaged:

| Fixed | Accepted (Free-Tier / scope) |
|---|---|
| EC2 account-default IMDSv2; S3 account-level Block Public Access | RDS Multi-AZ / deletion protection / enhanced monitoring / IAM DB auth; customer-managed KMS keys; CloudTrail-dependent audit alarms; NAT instance carries a public IP and is not SSM-managed (it is a minimal appliance) |

## Compliance frameworks addressed

- **CIS AWS Foundations Benchmark 2.0** — measured by Prowler; the majority of
  applicable Identity, Logging, and Networking controls pass. Gaps are the
  CloudTrail-based monitoring controls (CloudTrail is out of scope for a
  Free-Tier lab) and account-hardening items outside this project's IaC.
- **AWS Foundational Security Best Practices** — a second Prowler scan is kept
  for cross-reference.
- Config rules map to CIS controls for SSH exposure (4.1/4.2), S3 public access
  (2.1.5), EBS encryption (2.2.1), RDS encryption, and VPC flow logging (3.9).

## Known risks and mitigations

| Risk | Mitigation | Residual |
|---|---|---|
| No TLS on the public endpoint | Out of scope (no domain). Only non-sensitive catalogue data is served; the demo checkout takes no payment | Traffic is cleartext — production must add ACM + HTTPS redirect |
| Single-AZ RDS | Daily automated backups; documented production path (Multi-AZ) | ~1 day RPO, minutes of RTO on AZ failure |
| Single NAT instance | Inbound path unaffected if it fails; `nat_mode = "gateway"` switch exists | Outbound internet lost until the instance is replaced |
| CI uses long-lived access keys | Dedicated user, scoped policy, keys in GitHub encrypted secrets, rotatable | Key compromise → project resources only, not the whole account |
| Schema seeding runs per instance | Idempotent (`CREATE TABLE IF NOT EXISTS`, `ON CONFLICT DO NOTHING`) | A slow race window on first boot; harmless |
| Plan file was tracked in git early in the project | Untracked, `.gitignore` fixed, both generated secrets rotated | See incident report 0002 |
| `alerts` SNS topic is unencrypted | CloudWatch Alarms cannot publish to a topic encrypted with the AWS-managed key `alias/aws/sns`; a customer-managed KMS key ($1/mo) is out of Free-Tier scope. The topic carries only alarm metadata (name, state, reason) — no secrets — published by an AWS service and consumed by an in-account Lambda | Alarm text readable if the account is compromised; production would use a CMK with a key policy authorising `cloudwatch.amazonaws.com` |
